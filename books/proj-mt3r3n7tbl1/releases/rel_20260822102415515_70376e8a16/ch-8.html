第 8 章

授权的边界

2005年初冬，一份发行协议被签署。一家拥有约四十名员工的北美独立工作室刚刚拿下了为Xbox 360开发第一人称射击游戏的合同。第七世代主机已经亮出硬件规格——Xbox 360的三核PowerPC架构、PlayStation 3的Cell异构多核设计——开发预算水涨船高，而引擎选型将决定未来两年整个团队的工作方式。

技术总监的办公桌上，两份授权协议并排摊开。一份来自Epic Games。Unreal Engine 3授权协议厚达数百页，装订成册，目录清晰。它涵盖的不只是渲染引擎的二进制使用授权——Unreal Editor的完整工具链许可、Kismet可视化脚本系统、Matinee过场动画工具、内置物理引擎、音频方案、网络复制层，以及针对Xbox 360多核架构的优化方案，全部列在条款清单里。版税结构采用阶梯式：前期授权费根据项目规模和目标平台浮动，商业发行后按净收入收取版税，超过特定销量阈值后比例上调。协议还附带可选的技术支持服务等级协议——Epic提供驻场工程师培训和定期工具链更新，费用另计。

另一份来自id Software。id Tech 4授权协议只有薄薄几页纸。核心条款极其简洁：被授权方获得引擎完整源代码的非独占使用权，可以自由修改渲染管线、物理集成、资源管理和工具链的任何部分。id Software不提供工具链维护承诺，不提供物理系统集成支持，不提供网络层方案。技术支持边界被明确定义为一行字：“源码即文档。”前期授权费显著低于UE3，没有版税阶梯，仅收取一次性固定费用。

两份合同并排放在桌上，构成了一道尖锐的选择题：引擎授权究竟卖的是什么？是技术本身，还是一整套生产管线？这个问题的答案，将决定谁能在第七世代主机战争中存活。

要理解这两份合同的深层差异，必须回到分歧的源头。第六章已经揭示了Epic与id Software在工具哲学上的根本对立——卡马克坚持“运行时优先”，编辑器是引擎的附属品；斯威尼则逐渐形成相反的信念，引擎的真正用户不是玩家，而是美术师与设计师。但2005年的授权条款显示，这种哲学分歧已经从技术架构层面蔓延到了商业模式层面，并且获得了各自的制度形态。

id Software的源码交付传统可以追溯到Quake引擎时代。1996年，当卡马克决定公开Quake引擎源码时，他的逻辑非常清晰：引擎的核心价值在于运行时代码的质量——渲染器的执行效率、内存管理的精密度、网络协议的延迟控制。工具只是辅助。一个顶尖的程序员团队拿到源码后，应该有能力自行构建或集成任何他们需要的工具链。id的角色是提供那份精密的技术图纸，而不是替授权方决定生产流程。

这种哲学在id Tech 2和id Tech 3时代运转良好。Valve拿到Quake引擎源码后，几乎重写了渲染器和动画系统，做出了《半条命》。Infinity Ward基于id Tech 3大幅修改，做出了《使命召唤》。这些成功案例强化了卡马克的信念：最好的授权方是那些有能力深度定制引擎的团队，而id应该保持技术精英主义的品质控制——少发授权，发就发给最顶尖的工作室，让他们在源码层面自行解决问题。

但到了2005年，产业环境已经变了。第七世代主机的硬件复杂度远超上一代。Xbox 360的三核六线程PowerPC架构要求引擎在任务调度上做出根本性的重新设计——渲染线程、物理线程和游戏逻辑线程必须能够真正并行执行，而不是依赖上一代单核时代的伪多任务。PlayStation 3的Cell处理器更加极端：一个主处理单元加上八个协处理单元，其中七个可供游戏使用。充分利用这种异构架构需要引擎在内存带宽管理、数据预取和并行渲染管线方面做出深层次的架构调整。

与此同时，游戏项目的团队规模急剧膨胀。一个典型的AAA项目不再由十几个人的精英小组完成，而是由上百人组成的跨专业团队协作推进。美术师和关卡设计师的数量开始数倍于程序员——这个比例在第七世代初期达到了三比一甚至四比一。这些非程序员需要每天在引擎中迭代内容：调整光照参数、摆放碰撞体、触发脚本事件、预览过场动画。如果每一个这样的操作都需要等待程序员修改文本配置文件或重新编译关卡，开发周期将不可控地拉长。

Epic比id更早感知到这种变化。斯威尼在2003年前后就开始调整UE3的设计方向。他将引擎定位为一套“中间件”——这个词在当时的游戏产业中刚刚开始流行，意指介于操作系统和游戏逻辑之间的完整软件层。中间件的核心承诺是：授权方不需要从零开始构建基础架构，而是直接在一个已经集成好的技术栈上开发游戏。UE3的中间件策略意味着Epic不仅提供渲染器，还提供物理引擎、音频引擎、网络层、资源管理系统，以及最重要的——一整套可视化的内容创作工具。

这套工具链的架构设计反映了Epic对第七世代开发流程的预判。Unreal Editor不是渲染器的附属品，而是一个独立的应用程序，拥有自己的窗口布局、快捷键体系和插件接口。Kismet可视化脚本系统允许关卡设计师在不写代码的情况下创建触发逻辑——将代表事件、条件和动作的节点拖拽到画布上，用连线定义执行流程。Matinee过场动画工具提供了基于时间轴的动画编辑能力，美术师可以在编辑器中直接调整摄像机运动、光照变化和角色动作，实时预览效果。内置物理引擎意味着碰撞检测和刚体模拟不需要额外集成第三方库——在编辑器中放置一个物体，它的物理属性就已经被定义好了。

这些功能各自都有技术代价。将物理、音频和网络层集成到引擎内部，意味着UE3的代码量远超id Tech 4的轻量级核心。运行时内存占用更高——在Xbox 360的512MB统一内存中，UE3的基础框架就要占用相当比例。某些垂直优化场景下的执行效率不如id的手动调优代码路径——当卡马克为单一硬件配置手工优化渲染管线时，他可以压榨出UE3的通用化架构无法达到的帧率。

但Epic赌的是另一件事。在第七世代的硬件上，开发效率的瓶颈不再是CPU周期，而是团队协作成本和内容迭代速度。一家中型工作室如果能用UE3的工具链让美术师在可视化编辑器中直接调整光照和碰撞体，而不必等待程序员修改配置文件，省下的时间远比多占用的几十兆内存更有价值。如果Kismet能让关卡设计师在一天内完成一个战斗遭遇的脚本逻辑，而不是占用程序员三天的时间来编写和调试Lua代码，项目周期就能缩短数周甚至数月。在开发成本以每月数十万美元计算的AAA世界里，这种效率差异直接转化为生存能力。

id Software看到了同样的产业趋势，但得出了不同的结论。卡马克并不否认工具链的重要性。他在2004年的一次内部讨论中明确谈到：第七世代的项目规模确实需要更好的工具，但工具链的构建责任应该由授权方自行承担。

他的推理基于一个技术判断——每个项目的需求不同，通用的工具链必然包含大量冗余功能，拖累运行时性能。一个专注于室内走廊射击的游戏不需要开放世界的流式加载系统。一个没有载具的游戏不需要物理引擎的车辆模拟模块。一个线性叙事的游戏不需要复杂的脚本系统。

如果引擎为了覆盖所有这些可能性而预先集成大量功能，那么每一个授权方都要为那些自己不需要的代码付出内存和CPU周期的代价。在id的哲学里，这是不可接受的妥协。

id Tech系列的核心竞争力——自Quake时代以来一直如此——是在给定硬件上压榨出最高的帧率和最低的延迟。卡马克的渲染器以对硬件资源的极致利用著称：手工优化的汇编代码、精确的内存预取策略、为特定GPU架构定制的着色器变体。这些优化只有在引擎保持轻量级核心的情况下才有可能。一旦开始为了通用性而添加抽象层和中间件集成，就会在每一个层面引入性能损耗——虚拟函数调用的开销、通用数据结构的冗余字段、为兼容性而保留的旧代码路径。

这是两种理性的冲突，而不是正确与错误的二分。

2005年，id Software宣布id Tech 4将延迟开源。这个决定暴露了源码交付哲学的另一个代价。id Tech 4使用了一种名为“卡马克反转”的阴影体优化算法。该算法的核心思想是通过模板缓冲区的深度测试优化来减少阴影体的填充率消耗——简单来说，它能在不增加额外渲染通道的情况下，大幅减少阴影渲染对GPU像素管线的压力。这个算法在2000年代初期的硬件上具有显著的性能优势，但它的专利状态在2004至2005年间正处于法律争议中。一家名为Creative Labs的公司声称拥有相关技术的专利权，尽管卡马克坚称他在独立研究的基础上发明了该算法。

卡马克的应对方式体现了id哲学的内在一致性：在公开源码之前，必须清理所有可能引发专利风险的代码。他不愿意让外部开发者在不知情的情况下承担潜在的专利侵权风险。这意味着整个id Tech 4的开源计划被推迟，直到法律问题得到澄清——这个过程最终持续了数年。这件事本身是负责任的。

但它产生了具体的产业后果：那些在2005年正在做引擎选型的工作室，无法及时获得id Tech 4的完整源码评估版本。他们只能看到id自家游戏《毁灭战士3》的技术演示，而没有机会在源码层面评估引擎的架构质量。而Epic已经在GDC上公开展示了UE3在Xbox 360上的运行效果，并且提供了可评估的工具链试用版——任何签署了保密协议的工作室都可以拿到一份包含完整编辑器的评估包。

转折发生在2006年3月的游戏开发者大会上。Epic的展台前聚集了数百名开发者。Cliff Bleszinski站在台上，手持Xbox 360手柄，实时操控着《战争机器》的主角马库斯·菲尼克斯穿过一片被战火撕裂的城市废墟。屏幕上，法线贴图的光照细节在角色盔甲的凹痕和划痕上流动，动态阴影随着掩体移动实时更新，粒子效果在枪火交战中炸裂，碎石的物理模拟在爆炸冲击波中自然散落。这一切都在Xbox 360的实机硬件上运行，帧率稳定在每秒三十帧——在当时的主机动作游戏中，这是一个可以接受的流畅度标准。

但真正改变现场气氛的不是画面质量。id Tech 4在阴影质量和帧率上仍有优势——《毁灭战士3》在PC上的动态阴影精度和六十帧的流畅度是UE3在2006年时还无法在主机上匹敌的。真正改变气氛的是Bleszinski接下来的动作。他打开了一个菜单。在游戏运行的同时，Unreal Editor的界面弹了出来。他当场选中了场景中的一堵掩体，拖拽它移动了数米，点击重新加载——整个过程不超过十秒。然后他切回游戏画面，角色立刻可以在新的掩体位置后蹲伏射击。那堵掩体的碰撞体、导航网格、光照探针和破坏效果，全部由工具链自动重新计算。一个关卡设计师不需要程序员协助，不需要重新编译关卡，不需要等待BSP刷子重建几何数据，就能完成这个迭代。

台下坐着的id Software工程师们看到了这一刻。他们看到的不是渲染技术的胜利。他们看到的是另一件事：Epic卖的不是渲染器，而是一整套已经被《战争机器》验证过的生产管线。《战争机器》不是UE3的技术演示——它是一个真实的AAA项目，经历了从概念设计到最终发行的完整开发周期。在这个过程中，Epic自己的开发团队每天都在使用UE3的工具链，每天都在遇到效率瓶颈，每天都在优化那些让美术师和设计师卡住的工具环节。当外部授权方拿到UE3时，他们拿到的不只是一套软件，而是Epic自己使用这套软件的经验和方法论——那些在真实开发压力下被反复打磨过的工具流程。

而id Tech 4要完成同样的掩体移动操作，需要设计师打开文本编辑器，找到掩体实体的坐标参数，修改X轴数值，保存文件，运行关卡编译器，等待BSP刷子重建整个关卡的几何数据，然后重新加载游戏。这个过程可能需要几分钟到几十分钟不等，取决于关卡的复杂度和编译器的处理速度。如果移动掩体后需要调整光照——因为掩体位置变了，阴影投射也随之改变——那么还需要重新计算光照贴图，这可能意味着数小时的离线烘焙时间。

这不是技术指标的比拼。这是生产管线成熟度的比拼。id Tech 4的源码交付模式在这个维度上有一个结构性的劣势：每个授权方都要从零开始构建自己的工具链——或者更准确地说，从id提供的那个极简编辑器开始，逐步添加自己需要的功能。id的编辑器本质上是引擎运行时的一个附属窗口，提供基本的几何操作和实体属性面板。它没有可视化脚本系统，没有过场动画编辑器，没有内置的物理调试工具。所有这些功能都需要授权方自行开发或集成第三方解决方案。

这个过程需要顶尖的程序员团队、充足的时间预算，以及愿意在引擎层面投入资源的发行商。在2005至2007年的产业环境下，同时具备这三个条件的工作室数量正在急剧减少。

原因很简单：第七世代主机的开发预算已经膨胀到了上一世代的两到三倍。发行商对项目周期和风险控制的敏感度远高于以往。一家中型工作室的引擎选型决策不再只是技术总监的个人偏好问题，而是涉及数百万美元投资回报率的商业计算。

如果选择id Tech 4意味着程序员团队需要花费六到八个月来构建和调试工具链，然后美术团队才能开始高效地产出内容，那么这六到八个月的额外开发周期——以及相应的工资支出和发行窗口延迟——必须被计入选型成本。而如果UE3的工具链可以让美术师在合同签署后的第二周就开始在编辑器中搭建关卡原型，那么前期授权费和后续版税即使更高，总成本也可能更低。

后果在接下来的两年中逐渐显现。UE3在第七世代主机战争中的生态扩张速度远超当时任何分析师的预期。Xbox 360的架构与UE3的设计方向高度亲和——三核PowerPC处理器适合UE3的多线程任务调度方案，DirectX 9的着色器模型3.0正好匹配UE3的法线贴图管线，Xbox Live的网络架构与UE3的复制层可以无缝对接。微软在2005年将UE3列为Xbox 360的首推中间件之一——这一举动不仅是技术认可，也是平台持有者向开发者发出的信号：如果你用UE3，你在Xbox 360上的技术支持路径将更加顺畅。

到2007年底，UE3的授权方名单已经覆盖了AAA领域的大部分主要工作室。BioWare用它做《质量效应》——一个以对话系统和剧情分支为核心的角色扮演游戏，UE3的Kismet脚本系统被深度用于管理对话树的逻辑。Rocksteady用它做《蝙蝠侠：阿卡姆疯人院》——一个以近战格斗和潜行移动为核心的动作游戏，UE3的动画蓝图系统被用于实现流畅的连击过渡。Irrational Games用它做《生化奇兵》——一个以水下城市为舞台的第一人称射击游戏，UE3的粒子系统和动态光照被用于营造幽闭恐怖的环境氛围。这些游戏在类型、风格和技术需求上差异巨大，但它们共享同一套引擎基础设施。

亚洲市场也在同步扩张。韩国NCSoft用UE3开发《剑灵》——一个以华丽武侠动作为卖点的MMORPG，UE3的网络复制层和资源流式加载系统在这个项目中经受了大规模多人在线的压力测试。日本Square Enix用它制作《最后的神迹》——一个以回合制战斗和宏大叙事为特色的角色扮演游戏，UE3的过场动画工具被用于实现复杂的剧情演出。甚至连中国的工作室也开始进入UE3的生态系统——尽管当时的中国市场主要还是以PC在线游戏为主，但UE3的通用化架构使得从主机到PC的跨平台移植成本相对可控。

而id Tech 4的授权生态则在萎缩。除了id Software自家的《毁灭战士3》和《雷神之锤4》，以及Raven Software等少数长期合作伙伴外，几乎没有新的AAA项目采用id Tech 4。部分原因是技术性的——id Tech 4的MegaTexture技术在第七世代主机上消耗了过多内存带宽。MegaTexture的核心思想是将整个关卡的纹理数据打包进一张巨大的纹理图集中，通过实时流式加载来消除纹理重复感。这个技术在PC上——特别是拥有256MB以上显存的高端显卡上——效果惊人。但在Xbox 360和PlayStation 3上，统一内存架构意味着纹理流式加载与游戏逻辑、物理计算和AI处理争抢同一块内存带宽。在开放场景下，MegaTexture的带宽消耗会导致帧率波动，而id的轻量级核心缺乏UE3那种通过预计算和缓存策略来缓解带宽压力的中间件层。

但更深层的原因是结构性的。愿意并且有能力从源码级别定制引擎的工作室越来越少。那些在Quake和id Tech 3时代能够独立维护引擎分支的顶尖程序员团队，正在被第七世代的开发规模所稀释——他们中的许多人被大发行商吸纳进了内部技术团队，或者加入了像Epic这样以引擎授权为主营业务的公司。而那些不具备这种能力的工作室在评估id Tech 4时，发现它缺少他们需要的工具链、物理集成和技术支持——不是因为这些功能无法实现，而是因为实现它们需要投入的时间和人才在预算表上无法被批准。

这不是id的失败。这是一种特定技术哲学在产业规模化压力下的自然收缩。

卡马克在2007年的一次访谈中坦率地谈到了这个问题。他说，id从来就不是一家为别人做工具的公司——“我们做引擎是为了做自己的游戏，授权只是副产品。”这句话精确地概括了两种模式的分野。

Epic将引擎本身视为产品——UE3的开发和维护不是《战争机器》的附属工作，而是一个独立的业务部门，拥有自己的产品经理、技术支持和销售团队。授权是主营业务，游戏开发是引擎的示范应用。

id则将引擎视为内部工具——id Tech 4的核心设计决策服务于id自家游戏的需求，授权方拿到的是id内部使用的同一套代码，没有为了通用性而添加的抽象层，也没有为了降低门槛而封装的功能。当产业需要的不再是一个精美的技术核心，而是一整套可以让上百人协作的生产管线时，副产品模式就失去了竞争力。这不是技术优劣的问题，而是产品定位的问题。

但这里必须避免一种简化的叙事：Epic成功而id失败。两种哲学各有其内在逻辑和代价。UE3的中间件策略降低了授权门槛，扩大了市场份额，但也付出了灵活性代价。那些深度依赖UE3的工作室，实际上将自己的技术栈绑定在了Epic的开发节奏上。当Epic决定将物理引擎从Ageia PhysX迁移到NVIDIA PhysX时——这个决定发生在2008年NVIDIA收购Ageia之后——所有使用UE3的项目都必须跟随迁移。这意味着重新测试所有物理相关的游戏逻辑，重新优化物理内存占用，重新处理与新版本PhysX的兼容性问题。当UE3的更新引入了与某个旧版本不兼容的工具链变更时，工作室要么升级并承担迁移成本，要么锁定旧版本并失去后续支持——而后续支持包括针对新硬件和新操作系统的优化补丁。

这种平台锁定效应在短期内是Epic的竞争优势。一旦一家工作室将生产管线建立在UE3的工具链之上，迁移到另一个引擎的成本就变得极高——不仅是技术迁移，还包括团队培训、资产转换和工作流重建。但在长期来看，它也在授权方中积累了一种隐性的不满。这种不满不会在单个项目周期内爆发——因为项目正在进行中，没有人会质疑已经做出的选型决定——但它会在下一个开发周期开始时浮出水面。当工作室开始评估下一款游戏的引擎选型时，他们会更仔细地计算锁定的代价。这种不满将在后来的UE4时代以开源和版税改革的形式得到回应——但那是另一章的故事了。

id Tech 4的源码交付模式则付出了生态规模的代价，但保留了技术纯粹性。拿到id Tech 4源码的工作室确实需要自行构建工具链。但一旦构建完成，他们拥有对引擎每一行代码的完全控制权。他们不会受到上游供应商的商业决策影响——当Epic的授权方被迫跟随PhysX迁移时，id Tech 4的授权方可以自行决定物理引擎的选型和集成方式。他们不会被迫跟随别人的技术路线图——如果某个UE3更新引入了一个对自家项目无用的功能但强制要求升级，UE3的授权方别无选择；id Tech 4的授权方可以自行选择合并哪些上游改动。他们不会在某天早上醒来发现自己的项目依赖了一个已经停止支持的中间件组件——因为从一开始，所有依赖项都在他们自己的控制之下。

这种自主性对某些项目来说价值巨大。特别是那些有特殊技术需求的军事模拟、工业可视化和研究项目——这些领域在第七章中已经展示了对游戏引擎的跨界兴趣。

美国海军的城市战训练系统需要精确的弹道模拟和建筑结构破坏模型，这些功能在通用游戏引擎中不存在，必须从源码级别定制。建筑可视化公司需要支持Revit和AutoCAD的数据格式，需要精确的光照模拟而不是游戏中的近似算法，需要处理比游戏关卡大几个数量级的几何数据。这些需求在UE3的封闭工具链中难以实现——因为引擎的底层假设是为游戏优化的，修改这些假设需要访问Epic没有开放的源码层。

事实上，id Tech 4在游戏领域之外的生命周期远超它在游戏领域之内，正是因为源码交付模式允许这些非游戏用户剥离不需要的游戏假设并注入自己的专业逻辑。当大多数AAA工作室在2010年前后已经转向UE3或新一代引擎时，id Tech 4的源码仍在军事承包商、建筑公司和研究实验室中被使用和修改。这不是id有意为之的多元化战略——这是源码交付哲学的自然副产品。

回到开篇那两张并排放在技术总监桌上的合同。2007年，那家中型工作室做出了选择。他们选择了UE3。不是因为UE3的渲染器比id Tech 4更好。事实上，他们的技术评估报告中有专门的一节对比了两款引擎的渲染质量。报告显示，id Tech 4在动态阴影精度、帧率稳定性和内存占用控制上仍有优势——卡马克的手工优化代码在特定硬件配置上确实能压榨出更高的性能。UE3在法线贴图质量和粒子效果丰富度上领先，但在阴影边缘的锐利度和帧时间的稳定性上不如id Tech 4。

他们选择UE3的原因写在了评估报告的结论部分。那段文字没有讨论渲染技术。它讨论的是团队构成：工作室只有十名程序员，却有二十五名美术师和关卡设计师。如果选择id Tech 4，程序员团队需要花费至少六到八个月来构建和调试工具链——不是写游戏代码，而是写让美术师能够工作的基础设施。然后美术团队才能开始高效地产出内容。而UE3的工具链可以让美术师在合同签署后的第二周就开始在编辑器中搭建关卡原型——不需要等待程序员完成任何前置工作。

评估报告还计算了另一个维度：风险。如果选择id Tech 4，工作室的技术能力将集中在少数几个核心程序员身上。如果他们中的任何一个在项目中途离开——这在游戏行业并不罕见——整个工具链的维护将面临严重风险。而UE3将这部分风险转移给了Epic——工具链的维护和更新由Epic的技术支持团队负责，工作室的程序员可以专注于游戏逻辑的开发。

这不是技术的胜利。这是生产管线的胜利。不是渲染器的胜利，而是编辑器的胜利。第六章所述的工具哲学分歧，在这一刻完成了它的商业化表达。Epic选择将复杂性封装在引擎内部，让授权方用金钱换取时间——前期授权费和后续版税，换来的是一个已经铺好的生产管线。id选择将复杂性暴露给授权方，让授权方用时间换取控制权——更低的授权费用和完全的源码自由，换来的是对每一行代码的自主掌控。而在第七世代主机的开发周期压力下——发行商要求更短的开发周期，更高的画面标准，更可控的风险——大多数工作室选择了用金钱换时间。

那家工作室的技术总监在评估报告的最后一页写下了一行备注。这行字不是技术分析，不是成本计算，而是一个判断：“我们不是在买引擎。我们是在买一条已经铺好的路。”

这句话无意中概括了整个时代的转向。引擎授权不再是一笔技术交易。它是一笔生产关系的交易。

授权方购买的不再是代码的产权或使用权——那些法律条款只是载体——而是进入一个标准化生产体系的资格。这个体系的边界由引擎供应商划定：哪些功能由引擎原生提供，哪些功能通过中间件集成，哪些功能留给授权方自行开发。规则由供应商制定：工具链的更新节奏、废弃功能的淘汰时间表、与新硬件的兼容性承诺。

升级节奏由供应商控制：何时迁移到新的物理引擎，何时放弃对旧平台的支持，何时引入可能破坏向后兼容性的架构变更。授权方节省了铺路的时间。但他们也接受了在路上行驶时必须遵守的交通规则。

2007年深秋，id Software发布了id Tech 5的首个技术演示。卡马克在新引擎中大幅强化了工具链——加入了可视化场景编辑器，改进了资源管线，提供了更完整的物理和音频集成。这些改变表明，即便是id也开始意识到生产管线在第七世代产业环境中的重要性。但此时的产业格局已经发生了不可逆转的变化：UE3已经在AAA领域建立了一个横跨北美、欧洲和亚洲的授权帝国。BioWare、Rocksteady、Irrational Games、NCSoft、Square Enix——这些名字覆盖了角色扮演、动作冒险、第一人称射击、大型多人在线和日式角色扮演等所有主要游戏类型。它们共享的不只是同一套渲染技术，而是同一套生产管线的基本逻辑。

而在这个帝国的边界之外，另一个力量正在积蓄动能。Unity——一个来自丹麦的小型引擎公司——在2005年6月的苹果全球开发者大会上首次公开展示了它的引擎。Unity不是中间件，也不是源码交付。它以完全不同的方式回答“引擎授权卖的是什么”这个问题：它卖的是门槛本身。不是进入AAA世界的门票，而是让任何有Mac电脑的人都能开始做三维游戏的可能性。当Epic和id在争夺AAA工作室的授权合同时，Unity正在开辟一个被双方都忽略的市场——独立开发者、小型团队、教育机构、网页游戏制作者。

但在2007年这个时间点上，引擎产业的基本格局已经被两份合同所决定。一份厚达数百页，卖的是生产管线。一份只有几页纸，卖的是技术自由。大多数工作室选择了前者。不是因为前者在技术指标上更优秀，而是因为第七世代的产业压力不允许大多数工作室承担后者的代价。这个选择不是关于技术优劣的判断，而是关于生存策略的计算。当开发预算膨胀到数百万美元，当发行窗口的延迟意味着错过圣诞销售季，当竞争对手正在用现成的工具链加速内容生产时，选择用时间换取控制权是一种奢侈——只有极少数拥有顶尖程序员团队和充足预算的工作室才能负担得起的奢侈。

那家中型工作室用UE3开发的游戏在2008年底发售。销量尚可，没有大赚也没有亏损——这是大多数AAA游戏的命运。技术总监后来离开了那家公司，加入了一家更大的发行商。他保留着那两份合同的副本，放在办公室书架的角落里。偶尔有新入行的程序员问起第七世代初期的引擎选型故事时，他会拿出那两份文件，让年轻人掂一掂它们的重量差异——几百页对几页，管线的承诺对自由的承诺，一条铺好的路对一片需要自己开拓的荒野。然后他会说：“选哪条路，取决于你想走多远，以及你想走多快。”

这就是2005至2007年间引擎产业分裂的深层逻辑。它不是一个关于成功和失败的故事，而是一个关于选择和代价的故事。两种技术哲学——封装复杂性与暴露复杂性，降低门槛与保持纯粹，卖管线与卖自由——各自做出了选择，各自承担了代价，各自定义了它们所服务的那一部分世界。在它们之间那道日益扩大的裂缝中，产业的基本规则已经被改写：引擎授权不再只是技术的买卖，而是生产关系的组织方式。而这个被改写过的战场，正在等待一个来自完全不同方向的闯入者。
